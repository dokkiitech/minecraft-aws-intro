# 03. EC2 — the game server itself

Files: `ec2.tf` / `user_data.sh.tftpl` / `server/`

EC2 (Elastic Compute Cloud) is AWS's virtual machine service. This chapter walks
through `ec2.tf` top to bottom, covering the main building blocks of an instance.

## AMI — the OS image

```hcl
data "aws_ami" "ubuntu_2404" {
  most_recent = true
  owners      = ["099720109477"] # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}
```

An AMI is the OS image an instance boots from. Its ID (`ami-xxxx`) differs per region
and per release, so we never hardcode it; we search for "the latest official Canonical
Ubuntu 24.04 (amd64)". Pinning `owners` matters: it prevents you from **accidentally
launching a third-party AMI with a look-alike name**.

## Instance type and CPU credits

We use `t3a.medium` (2 vCPU / 4 GB). The reasoning is itself a lesson in EC2:

- **The Bedrock server (BDS) ships x86_64 builds only** → cheap ARM (Graviton) is out
- t-family instances are "burstable": cheap at baseline, spending CPU credits to burst
- **`cpu_credits = "unlimited"`** is set. T3a credits persist for seven days after a
  stop, but `standard` throttles to baseline (40% of 2 vCPUs) after the balance is
  depleted. Unlimited avoids that throttle but can incur uncapped surplus charges;
  auto-stop limits exposure and the budget watch (chapter 07) alerts on excess cost

"Cheap instance + run only while playing" is the cost strategy backbone of this design.

## Security group — the firewall

```hcl
ingress {
  from_port = 19132
  to_port   = 19132
  protocol  = "udp"
  cidr_blocks = ["0.0.0.0/0"]
}
```

A security group is a per-instance firewall. **Only Minecraft's IPv4 UDP 19132 is
open. SSH (TCP 22) is not.** When you need a shell, use SSM Session Manager
(chapter 04). The strongest SSH hardening is not opening the port at all.

## EBS — the disk

A 20 GB encrypted gp3 volume holds the world data. The important fact: **EBS is billed
even while the instance is stopped** (~$1.90/month). In a month with zero play time,
this is essentially your whole bill.

## user_data — automated first-boot setup

`user_data` is a script that runs once on the instance's first boot.
What `user_data.sh.tftpl` does:

1. Installs required packages and AWS CLI v2
2. Writes Terraform-provided values (bucket name, domain, idle minutes, …) to
   `/etc/mc-ondemand.env`
3. Fetches operational scripts and systemd units from S3's `bootstrap/`
   (the bootstrap pattern, chapter 05)
4. Downloads the latest Minecraft server build and enables everything
   (`systemctl enable --now`)

There is zero "SSH in and set things up by hand" — **creating the instance produces a
working game server**. The in-server machinery (DNS updates, the watchdog, automatic
backups) lives in the `server/` directory; each script is tens to a few hundred lines
and worth a read.

## IMDSv2 — instance metadata

```hcl
metadata_options {
  http_tokens = "required"
}
```

From inside EC2, `169.254.169.254` serves the instance's own metadata (IP, credentials,
…) — the IMDS. The old v1 was a classic SSRF hole for stealing credentials, so
requiring **token-based v2 only** is current best practice. This project uses IMDS at
boot to learn its own public IP for the DNS update.

## The decision not to use an Elastic IP

The obvious way to give a server a fixed IP is an Elastic IP — but **EIPs are billed
while the instance is stopped**, the worst possible match for a server that is almost
always stopped.

Instead, on every boot the instance writes its new dynamic public IP to a Cloudflare
A record with TTL 60 (`server/cloudflare-update.sh`). From the client's point of view,
`mc.example.com` always points at the right IP.

> Note: Cloudflare's proxy (orange cloud) does not pass UDP. This record must be
> **DNS only (grey cloud)** — records auto-created by the script are DNS only.

## Cloudflare or Route 53 — either is fine

The code in this repo targets Cloudflare, but **either choice is fine**. If you want to
stay entirely inside AWS, rebuilding on Route 53 is perfectly reasonable. This project
uses Cloudflare because of how it plays with **managing all infrastructure as code**:

1. **DNS lives outside the app stack.** Your domain outlives this Minecraft server.
   With DNS on a separate provider (separate stack), `terraform destroy` on this
   project cannot touch the zone, and you can safely share the zone with other
   projects (websites, email). This is chapter 02's "stack = blast radius" in practice
2. **Cloudflare is Terraform-manageable too.** Its official provider is mature, so DNS
   stays in code (the repository this project came from manages all DNS in a
   `cloudflare/` stack). "Outside AWS" does not mean "manual"
3. **Finely scoped API tokens.** The token the instance holds can only edit DNS in one
   zone (chapter 08). If it leaks, the damage is limited to that zone's records
4. **Free.** Route 53 costs $0.50/month per hosted zone plus query charges;
   Cloudflare DNS is free

Route 53 has its own clear advantage: no external token at all — just add
`route53:ChangeResourceRecordSets` to the EC2 role, and the SSM secret disappears.
If your domain is already on Route 53, keep it there. Porting means replacing
`cloudflare-update.sh` with `aws route53 change-resource-record-sets` — a nice
exercise if you want one.
