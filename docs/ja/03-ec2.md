# 03. EC2 — ゲームサーバー本体

対応ファイル: `ec2.tf` / `user_data.sh.tftpl` / `server/`

EC2(Elastic Compute Cloud)は AWS の仮想マシンです。この章では `ec2.tf` を上から読みながら、
EC2 の主要な構成要素を押さえます。

## AMI — OS のイメージ

```hcl
data "aws_ami" "ubuntu_2404" {
  most_recent = true
  owners      = ["099720109477"] # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}
```

AMI はインスタンスの起動元になる OS イメージです。ID(`ami-xxxx`)はリージョンごと・更新ごとに
変わるのでハードコードせず、「Canonical 公式の Ubuntu 24.04 (amd64) の最新」を検索して使います。
`owners` を指定するのは、**名前だけ似せた第三者の AMI をつかまされないため**です。

## インスタンスタイプと CPU クレジット

`t3a.medium`(2 vCPU / 4GB)を使います。選定理由がそのまま EC2 の勉強になります:

- **Minecraft 統合版サーバー(BDS)は x86_64 ビルドしか無い** → 安い ARM(Graviton)は使えない
- t 系は「バースト可能」インスタンス。普段は安く、CPU クレジットを消費して性能を出す
- **`cpu_credits = "unlimited"`** にしている。T3a のクレジットは停止後 7 日間保持されるが、
  `standard` は残高を使い切るとベースライン(2 vCPU 合計 40%)に絞られる。
  unlimited はその制限を避ける代わりに上限のない超過料金が発生しうるため、
  自動停止で稼働時間を抑え、予算監視(07 章)で使いすぎを検知する

「安いインスタンス + 使うときだけ起動」がこの構成のコスト戦略の柱です。

## セキュリティグループ — ファイアウォール

```hcl
ingress {
  from_port = 19132
  to_port   = 19132
  protocol  = "udp"
  cidr_blocks = ["0.0.0.0/0"]
}
```

セキュリティグループはインスタンス単位のファイアウォールです。**開けるのは Minecraft の
IPv4 UDP 19132 だけ。SSH(TCP 22)は開けません。** シェルが必要なときは
SSM Session Manager(04 章)を使います。「そもそもポートを開けない」のが最強の SSH 対策です。

## EBS — ディスク

ワールドデータが乗る暗号化済み 20GB の gp3 ボリューム。重要なのは、
**EBS はインスタンス停止中も課金される**ことです(約 $1.9/月)。
この構成の「遊ばない月」の固定費はほぼこれだけです。

## user_data — 初回起動時の自動セットアップ

`user_data` はインスタンス初回起動時に一度だけ実行されるスクリプトです。
`user_data.sh.tftpl` が行うこと:

1. 必要パッケージと AWS CLI v2 のインストール
2. Terraform から渡された値(バケット名・ドメイン・自動停止分数など)を `/etc/mc-ondemand.env` に書く
3. S3 の `bootstrap/` から運用スクリプトと systemd unit を取得して配置(05 章の bootstrap パターン)
4. Minecraft サーバー最新版のダウンロードと常駐化(`systemctl enable --now`)

「人が SSH して手作業でセットアップ」を一切なくし、**インスタンスを作れば勝手にゲームサーバーに
なる**状態にしています。サーバー上で動く仕掛け(DNS 更新・watchdog・自動バックアップ)は
`server/` ディレクトリの各スクリプトを読んでみてください。それぞれ数十〜数百行です。

## IMDSv2 — インスタンスメタデータ

```hcl
metadata_options {
  http_tokens = "required"
}
```

EC2 の中からは `169.254.169.254` で自分の情報(IP、認証情報など)を取れます(IMDS)。
旧方式(v1)は SSRF 攻撃で認証情報を抜かれる定番の穴だったため、**トークン必須の v2 のみ**に
制限するのが現在のベストプラクティスです。この構成では起動時に自分の Public IP を IMDS から
取得して DNS に登録するのに使っています。

## EIP を使わない、という設計判断

サーバーの IP を固定する素直な方法は Elastic IP ですが、**EIP はインスタンス停止中に課金されます**。
「ほぼ止まっているサーバー」であるこの構成とは相性が最悪です。

代わりに、起動のたびに変わる動的 Public IP を、EC2 自身が起動直後に Cloudflare の
A レコード(TTL 60 秒)へ書き戻します(`server/cloudflare-update.sh`)。
クライアントから見れば `mc.example.com` は常に正しい IP を指します。

> 注意: Cloudflare のプロキシ(オレンジ雲)は UDP を通しません。
> このレコードは必ず **DNS only(グレー雲)** にします(スクリプトが自動作成する場合は DNS only になります)。

## DNS は Cloudflare でも Route 53 でもいい

この教材のコードは Cloudflare 前提ですが、**どちらを選んでも構いません**。AWS の中で
完結させたければ Route 53 で組み直すのも普通にアリです。そのうえで、この教材が
Cloudflare を採用しているのは、**IaC でインフラ全体を管理する前提**に立ったときの扱いやすさです。

1. **DNS をアプリのスタックから分離できる。** ドメインは Minecraft サーバーより長生きする
   資産です。DNS を別プロバイダ(別スタック)に置いておけば、この構成を `terraform destroy`
   で丸ごと消してもゾーンは無傷で、他のプロジェクト(Web サイトやメール)と同じゾーンを
   安心して共有できます。02 章の「スタック = 影響範囲」の実践です
2. **Cloudflare も Terraform で管理できる。** 公式の Terraform プロバイダが成熟しており、
   ゾーンやレコードをコードで管理する運用にそのまま乗ります(この教材の元リポジトリでも
   DNS 全体を `cloudflare/` スタックでコード管理しています)。「AWS の外だから手作業」には
   なりません
3. **権限を細かく絞ったトークンを発行できる。** EC2 に持たせるのは
   「対象ゾーンの DNS 編集だけ」ができる API トークンです(08 章参照)。漏えいしても
   被害はそのゾーンの DNS 書き換えまでに限定されます
4. **無料。** Route 53 はホストゾーンごとに $0.50/月 + クエリ課金。Cloudflare の DNS は
   無料プランで足ります

一方 Route 53 には、外部トークンが不要になる(EC2 ロールに
`route53:ChangeResourceRecordSets` を付けるだけで済み、SSM にシークレットを置く必要も
なくなる)という明確な利点があります。すでに Route 53 でドメインを管理しているなら
そのままでどうぞ。`cloudflare-update.sh` を `aws route53 change-resource-record-sets` に
置き換えれば移植できるので、腕試しの改造課題にもちょうどいいです。
